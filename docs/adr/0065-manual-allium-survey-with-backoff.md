# ADR0065 — 사용자 승인 Allium 수동 단발 조사와 지수 백오프

## 승인과 범위

2026-10-23 사용자는 과금 통제 미확인 안내 뒤 “우선 실행해줘. 안되면 최적화하면 되닌깐”으로 최초 실행을 승인했고 실패 재시도에 “지수백오프 형식으로”를 지정했다. 이번 명시적 승인을 ADR0061의 공급자 강제 한도 증명 요구에서 별도 수동 경로만 예외로 반영한다. 한도·초과 과금 설정·실행 비용은 계속 UNCONFIRMED이며 HTTP 횟수를 비용 상한으로 표시하지 않는다. 자동 일별/5분 Allium 수집·DB import·웹 기본 공급자 변경은 승인 범위에 포함하지 않는다.

## 실행과 영속 예약

기존 `execute`의 strict 검사는 유지하고 `execute-manual`을 추가한다. 같은 고정 root의 당일 성공 usage 원문·영수증·키 동일성, 승인 원문 hash, 별도 authorization hash, 고정 plan/SQL/결과 상한을 결합한다. 기존 usage는 저장된 맥락만 제공하며 잔여 예산 인증이나 새로운 관측으로 취급하지 않는다. usage 재조회는 없다. 수동 승인은 발급 후 15분 및 당일 안에서만 유효하며 매 dispatch 직전 검사한다.

두 실행 경로는 공통 원자적 예약 잠금을 사용한다. 수동 경로는 기존 period/survey/manual 예약이 있으면 거부한다. 수동 예약은 키·날짜에 관계없는 영속 `manual-once` 표식을 만들어 이후 양 경로의 실행을 차단한다. 실패·프로세스 중단에도 표식과 예약을 삭제하지 않는다. 예약 잠금 중 프로세스가 종료돼도 자동 해제하지 않는다. 이 제어는 같은 PC의 고정 로컬 root에 한정된다.

## 재시도

수동 GET의 일시적 네트워크 오류, HTTP 408/429/500/502/503/504에 최초 시도 뒤 최대 3회 재시도한다. 대기는 2/4/8초에 0~250ms 지터를 더하고 Retry-After의 초 또는 HTTP-date가 요구하는 최소 대기보다 짧지 않다. 60초 초과 대기는 중단한다. 대기 후에도 승인 만료와 HTTP 잔여 횟수를 다시 확인한다. JSON·스키마·권한·크기·디스크 오류와 관리형 프록시 차단은 재시도하지 않는다.

SQL 생성·실행 POST는 응답 유실·서버 오류·429만으로 미접수를 증명할 수 없어 자동 재전송하지 않는다. run ID가 확보되면 같은 실행의 상태 조회에 백오프를 적용한다. ID 미확보나 실패 원인 미확정은 UNKNOWN으로 보존한다. SQL 실패는 원인 검토 대상으로 남기고 같은 SQL을 자동 반복하지 않는다.

고정 세 SQL의 접수 실행은 최대 3회다. authorization의 보수적 HTTP 상한은 156이며 현재 POST 재전송 없는 제어 흐름의 최대는 138회(생성3+실행3+상태120+결과12)다. 매 시도의 intent를 전송 전에 보존하고 원문·응답 코드·hash·백오프 대기를 비공개 archive에 남긴다. 기존 strict 경로의 39HTTP/재시도0은 유지한다.

## 검토와 검증

Router Lead `fef7e1d1cf1e42c3a86068a6417011d5`의 proceed와 재시도 검토 `0912d12a17c84fdaa52e6e976a56ce79`의 revise_plan 조건을 반영한다. 후자의 POST 미접수 보장 요구에 따라 POST 자동 재전송을 제외했다. 검토는 사용자 승인이나 실행 성공의 대체가 아니다. 실제 호출·결과·시험 수는 이번 단위 인계문에 기록한다.
