# 0130 — TXID-backed Wallet Flow MVP

2026-11-04. User authorizes development and existing CI/CD, not schema/security/payment changes.

Separate manual collector → immutable private response/intent/hash store → normalized events → pure graph/role/resource analysis → readonly snapshot API → Atlas page. Existing collectors, schedules, PostgreSQL schemas and credentials remain untouched. Early manual collection uses a reviewed public projection bundled with a release. The browser reads stored observations; entering an unknown TXID never silently starts network collection. A later independent PostgreSQL schema could store immutable snapshots, raw evidence references, event keys and labels with existing reader access; no migration is executed or required for this file-backed MVP. Regular collection is deferred.

No pre-existing Upbit seeds/TXIDs were found initially. A subsequently user-provided seed led to a bounded real deposit/sweep/resource snapshot. User identity/address association and source responses remain private; public normalized observations contain no asserted ownership labels. Empty state must not invent Upbit ownership or populate fixture transactions. Fixtures are explicitly test-only and rejected by the production snapshot reader.

Amounts remain integer decimal strings; arithmetic uses bigint. TRC20 Transfer logs are decoded only for the pinned TRON USDT contract, with log index preserving multiple same-TX events. Receipts and transaction body IDs/status bind the event. Failed transactions retain fees/status but produce no fund/resource movement events. Native TransferContract and Stake2 Delegate/UnDelegate are different event kinds. Delegation balance is staked SUN, not transferable TRX or a number of Energy units. Current address balance has a separate observation time, no historical balance claim.

Edges carry event IDs, distinct TXIDs, exact amount and period. Time-respecting paths advance strictly to later blocks and remain candidates. No fungible unit provenance after pooling, shared ownership from connectivity, or withdrawal/customer/internal classification from direction alone. Roles include evidence and counter-evidence; reserve/cold/hot and newly created operational address claims remain unknown. Resource triplets use the same receiver and resource, with TXIDs and receipts, and remain temporal associations rather than proven cost savings.

Provider and limits: manual fixed TronGrid mainnet origin, account index for bounded discovery, solidified body+receipt for event evidence, no retries/redirects/provider fallback. Max4 expanded addresses,24 verified transactions,2×50-row pages per address/feed,80HTTP,16MiB total,2MiB response,300s,1.1s minimum interval,1–24h total window. Headers never enter logs. A supplied key requires an explicit confirmed-free-tier marker; no paid key is presumed free. Quota/pricing must be checked before live collection. Consumed failed run directories cannot be reused. Partial pages/unexpanded counterparties, provider-index limits, incoming delegation completeness and uncollected internal TRX are stated, not interpreted as absence.

API is GET/HEAD-only, within existing Host/Origin/CSP boundaries. New fixed assets/read endpoint are added to the normal publication allowlist; existing security checks are not weakened. No arbitrary URLs, writes, auth policy or provider access in web requests. Publication verifies raw hashes and re-normalizes receipts before exporting; raw responses/keys never enter Git/public routes.
